# Zero-dependency resume roasting app with Claude integration

A greenfield Node.js web app that accepts resume text (pasted or uploaded as PDF/DOCX/TXT), sends it to Claude for analysis at configurable intensity levels, and renders structured feedback in a fire-themed SPA. The entire stack uses zero external dependencies — custom HTTP server, custom router, custom multipart parser, custom file parsers, all built on Node.js built-in modules.

Watch for: Path traversal bypass in static file serving (confirmed). No request body size limit on any endpoint (confirmed). PDF/DOCX parsers silently return empty strings on failure, which produces a confusing "not enough words" error instead of surfacing the real problem (confirmed).

## High-level view

The static file server strips `..` sequences with a naive regex replace that doesn't account for patterns like `....//` that survive a single pass, leaving a path traversal gap that could expose files outside the public directory.

The backend has no upper bound on request body size. A client can POST an arbitrarily large payload to `/api/roast` and the server will buffer it entirely into memory before any validation occurs. The rate limiter throttles request count but not payload size, making memory exhaustion straightforward.

The file parsing layer (PDF, DOCX) catches all errors and returns empty strings rather than propagating failures. Most real-world PDFs use encoding schemes this parser can't handle, so users uploading valid files get a misleading "must contain more than 50 words" error instead of a clear "we couldn't read your file."

The prompt schema was updated mid-development to align with the frontend's expected response shape. The fix is correct, but the test suite doesn't exercise the Claude client, roast handler, or multipart parser at all — the most critical integration paths have zero coverage.

The rate limiter uses `req.socket.remoteAddress` with a fallback to `x-forwarded-for`. Behind a reverse proxy (common in production), all clients share the proxy's IP and thus one bucket, making rate limiting ineffective.

## Path traversal in static file serving

The static file handler in `server/index.js` attempts to prevent directory traversal:

```javascript
const safePath = pathname.replace(/\.\./g, '');
const filePath = join(PROJECT_ROOT, 'public', safePath);
```

The pattern `....//` becomes `../` after one replace pass — the regex removes the inner `..` leaving the outer dots and slash to form a new traversal sequence. The URL is already percent-decoded by `new URL()`, so raw `%2e%2e` would arrive as `..` and be caught, but the nested-dot bypass survives. The correct approach is to resolve the full path with `path.resolve` and verify it starts with the intended public root.

The SPA fallback also serves `index.html` for any non-existent path, meaning a request to `/api/nonexistent` (not caught by the router because it only matches exact registered paths) returns HTML with a 200 rather than a JSON 404.

## Unbounded request body buffering

Both `Router.parseJsonBody` and `Router.parseRawBody` accumulate all incoming chunks without a size gate:

```javascript
static parseRawBody(req) {
  return new Promise((resolve, reject) => {
    const chunks = [];
    req.on('data', (chunk) => chunks.push(chunk));
    req.on('end', () => resolve(Buffer.concat(chunks)));
  });
}
```

A single multi-gigabyte POST is enough to crash the process. The rate limiter permits 5 requests per IP before throttling, but one oversized request suffices. Resumes should never exceed a few megabytes; a 10MB cap with a 413 response would close this gap.

## Silent failure in file parsing

```javascript
function parsePdf(buffer) {
  try {
    // stream extraction, decompression, Tj/TJ text extraction
    return textParts.join(' ').replace(/\s+/g, ' ').trim();
  } catch {
    return '';
  }
}
```

The PDF parser only handles uncompressed or FlateDecode streams with simple BT/ET text blocks and Tj/TJ operators. PDFs using CIDFont mappings, ToUnicode tables, or content streams split across multiple objects will yield empty or garbage text. The DOCX parser has the same empty-string-on-failure pattern.

The roast handler's subsequent word-count check (`wordCount <= 50`) then fires with "Resume text must contain more than 50 words" — a baffling message for someone who uploaded a 3-page PDF. The handler should distinguish between "text too short" and "file could not be parsed" by checking whether a file was uploaded and the parse result was empty.

## Rate limiter IP resolution

```javascript
const ip = req.socket.remoteAddress || req.headers['x-forwarded-for'] || 'unknown';
```

When deployed behind nginx, a load balancer, or any reverse proxy, `remoteAddress` is the proxy's IP for every client. All users share one 5-token bucket. The header order should be reversed (prefer `x-forwarded-for` when a trusted proxy is configured), or the trust mode should be explicit via an env var like `TRUST_PROXY=true`.

## Test coverage gaps

No tests exist for `claudeClient.js`, `routes/roast.js`, or `multipart.js`. The Claude client contains pure-function logic that's trivially testable without network access: `extractAndParseJson` (JSON extraction from fenced/unfenced responses), `validateResponse` (schema validation), and `getSystemPrompt` (prompt construction per intensity). The multipart parser is similarly pure — Buffer in, structured fields/files out — and handles security-sensitive binary parsing.

The schema mismatch that was fixed in this diff (sections had `{title, score, feedback}` but the frontend expected `{section, issues: [...]}`) would have been caught by a single test asserting the prompt's schema matches the frontend's rendering expectations.
