# Resume Roaster security and test coverage fixes (v2)

The v1 review raised five issues: path traversal in static serving, unbounded body buffering, silent file parse failures, missing test coverage for critical paths, and rate limiter ineffectiveness behind a proxy. All five have been addressed. The path traversal fix uses `path.resolve` with a prefix check, body parsing enforces a 10MB limit with 413 responses, the roast handler returns 422 when file parsing yields no text, 40 new tests cover the multipart parser, Claude client pure functions, and roast handler validation, and the rate limiter now prefers `x-forwarded-for`.

Watch for: Rate limiter trusts `x-forwarded-for` unconditionally, allowing clients to spoof their IP and bypass rate limiting when no reverse proxy is present (confirmed). The body size enforcement can emit data events after `req.destroy()` is called, potentially pushing additional chunks before the stream fully closes (likely).

## High-level view

The path traversal and body size fixes close the security gaps from v1. The SPA fallback now correctly returns JSON 404 for unmatched `/api/*` paths instead of serving `index.html`.

The rate limiter now prefers `x-forwarded-for` over `remoteAddress`, but trusts the header unconditionally — a direct client (no proxy in front) can forge the header to evade or weaponize rate limiting against other IPs.

## Unconditional x-forwarded-for trust

```javascript
const ip = req.headers['x-forwarded-for']?.split(',')[0]?.trim() || req.socket.remoteAddress || 'unknown';
```

When the app runs without a reverse proxy (local dev, direct exposure), any client can set `X-Forwarded-For: 1.2.3.4` to get a fresh rate limit bucket on every request, or set it to a victim's IP to exhaust their bucket. The standard mitigation is a `TRUST_PROXY` environment variable — when false or absent, ignore the header and use `remoteAddress`; when true, use the header. Low-severity for a side project but worth documenting as a deployment assumption.

## Body size enforcement timing

```javascript
req.on('data', (chunk) => {
  totalSize += chunk.length;
  if (totalSize > maxSize) {
    req.destroy();
    reject(Object.assign(new Error('Request body too large'), { statusCode: 413 }));
    return;
  }
  chunks.push(chunk);
});
```

After `reject` fires, the Promise is settled. But `req.destroy()` is asynchronous — already-queued `data` events in the event loop may still fire. On subsequent callbacks, `totalSize > maxSize` remains true, `reject` is a no-op on the settled Promise, and the early `return` prevents `chunks.push`. The only observable effect is `req.destroy()` called multiple times, which is idempotent. Safe in practice, but a `let destroyed = false` guard would make the intent explicit.
